# Рабочие допущения MVP

> **Важно.** Перечисленные ниже решения — выбранная командой реализация MVP, а **не требования исходного ТЗ ФСП**.
> Они ещё не согласованы с организаторами. Если организаторы дадут другие ответы, изменения вносятся в
> перечисленные политики и сервисы без переписывания интерфейса и схемы БД.

## 1. Решения, подтверждённые владельцем проекта

| Решение | Источник |
|---|---|
| Frontend — Next.js, backend — NestJS, БД — PostgreSQL | решение команды |
| Четыре специализации: frontend-разработчик, backend-разработчик, ML-инженер, manual QA | решение команды (ТЗ: «на этапе MVP достаточно основных направлений») |
| Внешние AI/LLM API не используются; локальная модель не является зависимостью | решение команды |
| Все демонстрационные и оценочные данные — собственная синтетика | ТЗ разрешает синтетику; решение команды |
| Заявленный грейд отделён от подтверждённого; до успешного теста кандидата нет в основной выдаче | решение команды, следует из ТЗ |
| Достижения ФСП — дополнительное преимущество, не замена требованиям | решение команды |

## 2. Допущения, требующие ответа организаторов

| Вопрос | Рабочее решение MVP | Где меняется |

| Зарплата | Целое число рублей в месяц до вычета налогов (GROSS), вилка «от–до» обязательна в потребности и приглашении | DTO потребности и приглашения |

| Условия попадания кандидата в поиск | Подтверждён email, заполнен профиль (включая дату рождения), активное согласие на публикацию, включена видимость, поиск не «на паузе», выбран хотя бы один заполненный канал для раскрытия; возраст 16+ (для 16–17 лет — согласие законного представителя). | Подтверждение email | Обязательно: до него доступны только экран подтверждения, повторная отправка письма и выход. Ссылка одноразовая, действует 24 часа (`EMAIL_VERIFICATION_TTL_HOURS`); GET по ссылке ничего не подтверждает — нужен явный POST | `auth`, `.env` |
| Вход | Email и пароль (Argon2id), серверная сессия 7 суток; восстановление пароля и вход через ФСП ID **не реализованы** | `auth`, `SESSION_TTL_HOURS` |
| Хранение и удаление данных | Сроки хранения и удаление по запросу не реализованы; сохранённые подборки хранят снимок результатов без контактов | `SelectionRun` |
| Язык и устройства | Интерфейс только на русском; адаптивная вёрстка для телефона (проверена автоматически эмуляцией 390 и 320 px в Chromium; реальные устройства, Safari и Firefox не проверялись) | `apps/web`, E2E 9 |
| Резюме | Загружаемое PDF-резюме — источник **предложений** для профиля, а не подтверждения: распознавание по правилам без ML, только PDF с текстовым слоем, файл не хранится; навыки и грейд остаются самоописанием | `domain/resume`, `modules/resume` |
| Короткие задания | Не чаще одного задания в неделю на кандидата, срок ответа 7 дней, не более 10 активных заданий на компанию; задание подбирается по **подтверждённой** квалификации; результат — сигнал регулярности («решено за 90 дней»), он не меняет грейд и не входит в формулу подбора; опубликованное задание не редактируется | `domain/tasks`, `modules/tasks` |
| Адресные задания | Работодатель может отправить своё активное задание конкретному видимому ему кандидату (вопросы 2 и 53), в том числе без подтверждённого грейда; не зависит от недельного периода; не более одного неотвеченного адресного задания от компании одному кандидату | `TasksService.assign` |
| Метка доверия компании | Добровольная проверка, не блокирующая основной сценарий (вопрос 41): ИНН (контрольные разряды), наличие в реестре, совпадение названия и домена почты аккаунта. В MVP — демонстрационный реестр вымышленных организаций; смена названия снимает метку | `domain/companies/verification.ts`, `CompanyRegistry` |
| Кандидаты 16–17 лет | Поддерживаются (вопрос 16): дата рождения обязательна для публикации; младше 16 — профиль не публикуется; 16–17 — нужно согласие законного представителя (в MVP — заявление кандидата с ФИО представителя); работодатель видит только отметку «16–17 лет» и при приглашении подтверждает особые условия труда (ТК РФ, гл. 42) | `domain/candidate/age.ts`, `InvitationsService` |

## 3. Технические допущения

- Справочники специализаций, групп компетенций и навыков задаются в коде с версией и синхронизируются в БД при старте API; первичный ключ — стабильный код (`BACKEND`, `sql`), а не UUID.
- Ограничение частоты запросов хранится в памяти процесса API (один экземпляр MVP); при горизонтальном масштабировании нужен общий счётчик (например, в PostgreSQL или Redis).
- Ранжирование выполняется в backend после SQL-фильтрации — допустимо для синтетического объёма; ограничения масштабирования описаны в `docs/matching.md`.
- Внешние HTTP-запросы приложения во время работы отсутствуют (кроме SMTP).
- Ограничения на повторные приглашения после отказа или истечения нет (ограничен только один активный), как и на повторные отклики после отзыва: защита от навязчивых и фиктивных предложений и массовых откликов требует проверки компаний, лимитов и модерации — вне MVP.
- В контейнерах режим `NODE_ENV` фиксирован (`production`), адрес SMTP внутри сети задаётся `DOCKER_SMTP_HOST`/`DOCKER_SMTP_PORT`: значения `.env`, рассчитанные на запуск на хосте (`localhost`), в контейнеры не передаются.
- В production значение `SESSION_SECRET` из `.env.example` отвергается при старте; для Docker-запуска секрет нужно сгенерировать (`openssl rand -hex 32`).

## 4. Вопросы к организаторам и полученные ответы

Ответы получены на встрече с участниками и письменно (коды — из таблицы ответов организаторов). Решения MVP сверены с ними.

| Вопрос | Ответ организаторов | Как в MVP |
|---|---|---|
| Несколько подтверждённых специализаций | Не требуется; для MVP достаточно одной категории, поддержка нескольких — плюс (VS.2) | Поддержано: кандидат виден в каждой подтверждённой категории; в карточке — выбранная категория и остальные |
| Шкала грейдов, пороги, сроки пересдачи | Грейд — уровень навыков, подтверждаемый тестом; стаж — атрибут профиля (VS.1); период ограничения выбирает команда, пример — месяц или два | Junior/Middle/Senior, пороги 75/50/90/75; повтор уровня — 30 дней, новая оценка — 90 дней, уровень ниже — сразу |
| Общий тест или под вакансию | Единый под категорию, но не с одинаковым пулом вопросов; задания под вакансию — отдельный необязательный блок (VS.5) | Параметризованный банк, уникальные экземпляры; задания работодателя (регулярные и адресные) — отдельно |
| Неподтверждённый грейд | Можно показывать со статусом «грейд не подтверждён»; официально грейд — только по тесту (FTT.4) | Кандидат без теста виден ниже подтверждённых, с пометкой, без балла |
| Достижения ФСП | Буст внутри подтверждённого грейда, не замена теста; дисциплины равноприоритетны, можно учитывать релевантность направления (E08) | Бонус 5 из 100, баллы за результат (участие/призёр/победа), учитываются только дисциплины, релевантные специализации |
| Регулярные задания | Адресно кандидату; челлендж на категорию не запрещён; способ оценки — на усмотрение команды (E09) | Регулярное предложение раз в неделю + адресная отправка; тест — автоматически, разбор — работодатель |
| Что видит работодатель до принятия | Закрыты только контакты; ФИО и места работы показывать допустимо (VS.4) | Строже минимума: до принятия скрыты и ФИО, ссылки, свободный текст опыта (снижение риска дискриминации и деанонимизации) |
| Валидация грейда | Test-retest одного профиля со сравнением грейдов и разделяющая сила заданий; симуляция на синтетике допустима (PR.1) | Реализовано: docs/validation-results.md, раздел 2.9 (каппа, матрицы, индекс D, чувствительность); ограничения — находка F6 |
| Проверка на списывание | Не требуется, но будет большим плюсом (FTT.4) | Реализованы информационные сигналы честности: серверные (слишком быстрое завершение и мгновенно решённые кейсы) и интерфейсные (уходы со вкладки, вставка, копирование задания); видны кандидату и работодателю, на грейд не влияют; это не прокторинг, легко обходится (docs/assessment.md, раздел 5) |
| LLM | Допустимы, в т. ч. зарубежные; риски 152-ФЗ — на команде (VS.3) | LLM не используются |
| Проверка компаний, ATS | Добровольная метка доверия допустима; ATS — концепция для доп. функционала (FTT.5) | Метка доверия по демо-реестру; ATS — концепция |
| Охват специализаций | Достаточно основных направлений; важнее сквозной путь (WA.1); дизайнеры — по желанию (WA.2) | 4 технические специализации × 3 грейда |

Остаются открытыми: тексты согласий, сроки хранения и удаление данных (организаторы назвали достаточной минимальную проработку 152-ФЗ); формат и доступ к реальному реестру ФСП.

## 5. Где менять решения

| Что менять | Где |
|---|---|
| Пороги, длительность, задержки пересдачи, навыки | новая версия политики в `apps/api/src/config/policies.ts`, выбор через `ASSESSMENT_POLICY_VERSION` |
| Веса формулы, вклад заявленного навыка, баллы ФСП | `MATCHING_FORMULAS`, `MATCHING_FORMULA_VERSION` |
| Срок действия приглашения | `INVITATION_POLICIES`, `INVITATION_POLICY_VERSION` |
| Тексты и версии согласий | `CONSENT_POLICY_VERSIONS` в `config/policies.ts` |
| Состав банка заданий | `apps/api/src/domain/assessment/bank/*` (новая версия семейства; затем `pnpm bank:manifest`, `pnpm validate:quality`) |
| Справочники специализаций, навыков, отраслей | `apps/api/src/domain/catalog/*` (синхронизируются в БД при старте) |
| Поля, видимые работодателю | `apps/api/src/domain/privacy/profile-view.ts` (и тест `privacy.int-spec.ts`) |
| Релевантность достижений ФСП | `apps/api/src/domain/matching/fsp-relevance.ts` |

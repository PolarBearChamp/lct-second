# Рабочие допущения MVP

> **Важно.** Перечисленные ниже решения — выбранная командой реализация MVP, а **не требования исходного ТЗ ФСП**.
> Они ещё не согласованы с организаторами. Если организаторы дадут другие ответы, изменения вносятся в
> перечисленные политики и сервисы без переписывания интерфейса и схемы БД.

## 1. Решения, подтверждённые владельцем проекта

| Решение | Источник |
|---|---|
| Frontend — Next.js, backend — NestJS, БД — PostgreSQL | решение команды |
| Четыре специализации: frontend-разработчик, backend-разработчик, ML-инженер, manual QA | решение команды (ТЗ: «на этапе MVP достаточно основных направлений») |
| Внешние AI/LLM API не используются; локальная модель не является зависимостью | решение команды |
| Все демонстрационные и оценочные данные — собственная синтетика | ТЗ разрешает синтетику; решение команды |
| Заявленный грейд отделён от подтверждённого; до успешного теста кандидата нет в основной выдаче | решение команды, следует из ТЗ |
| Достижения ФСП — дополнительное преимущество, не замена требованиям | решение команды |

## 2. Допущения, требующие ответа организаторов

| Вопрос | Рабочее решение MVP | Где меняется |
|---|---|---|
| Сколько специализаций у кандидата | В интерфейсе одна активная специализация; модель данных хранит независимые квалификации по каждой специализации | `CandidateQualification` (уникальность candidate+specialization), UI профиля |
| Грейды | `JUNIOR`, `MIDDLE`, `SENIOR`; в UI — «грейд по результатам тестирования» | справочник `apps/api/src/domain/catalog` |
| Первичная неудача | Подтверждённого грейда нет, кандидата нет в поиске | политика оценки `assessment-policy-v1` |
| Переход на уровень ниже после неудачи | Сразу, если для этого грейда нет собственной задержки | `domain/assessment/eligibility.ts` |
| Повтор того же грейда | Не раньше 24 часов после завершённой неуспешной попытки (FAILED / EXPIRED / ABANDONED) | `assessment-policy-v1.retryCooldownHours` |
| Смена подтверждённого грейда | Не раньше 90 дней после последнего подтверждения | `assessment-policy-v1.reassessmentDays` |
| Высокий балл | Не повышает грейд автоматически; предлагается отдельный тест на следующий уровень после доступной даты | `domain/assessment/scoring.ts` (рекомендации) |
| Провал повторной оценки | Не понижает и не удаляет подтверждённый грейд | `AssessmentsService.finalize` |
| Пороги прохождения | Общий балл ≥ 75 и каждая группа ≥ 50; «уверенно» — ≥ 90 и каждая группа ≥ 75. Пороги конфигурируемы и **не являются научно откалиброванными** | `assessment-policy-v1` |
| Подтверждение навыка (skill tag) | Навык оценён минимум в 2 разных кейсах и результат по нему ≥ 70 | `assessment-policy-v1.skillEvidence` |
| Длительность теста | 30 минут, 6 мини-кейсов (по 2 на группу), ≥ 12 оцениваемых частей | `assessment-policy-v1` |
| Извлечение навыков из вакансии | Структурированная форма и справочник навыков; NLP-разбор свободного текста не выполняется | форма потребности, `catalog` |
| Тест «под работодателя» | Предпросмотр плана теста из структурированных требований в рамках общей матрицы; отдельные обязательные экзамены под работодателя отложены | `domain/assessment/blueprint.ts` |
| Приватность до согласия | Структурированная обезличенная карточка без ФИО, прямых контактов, внешних ссылок и произвольных текстов | `ProfilePresenter` (режим `EMPLOYER_REDACTED`) |
| Формула подбора | `score = 70·preferredFit + 25·assessmentQuality + 5·fspEvidence` после жёстких фильтров | `matching-formula-v1` |
| Бонус ФСП | Участие — 1, призёр — 2, победа — 3; по одному мероприятию учитывается сильнейшая запись; `min(sum/6, 1)` | `fsp-relevance-v1`, `matching-formula-v1` |
| Срок действия приглашения | 14 дней | `invitation-policy-v1.ttlDays` |
| Email локально | Реальное письмо в локальный Mailpit; для внешнего стенда — SMTP через переменные окружения | `.env`, `MailModule` |
| ФСП | Демонстрационный провайдер `MockFspProvider` и синтетические достижения, явно помеченные как демонстрационные | `FSP_PROVIDER`, `data/fixtures/fsp-mock.json` |
| Один работодатель — одна компания | Аккаунт работодателя управляет одной компанией; расширение до нескольких сотрудников описано в `docs/architecture.md` | `Company.ownerUserId` (unique) |
| Зарплата | Целое число рублей в месяц до вычета налогов (GROSS), вилка «от–до» обязательна в потребности и приглашении | DTO потребности и приглашения |
| Состав и размер банка | 24 семейства (по 6 на специализацию, по 2 на группу), 72 пары «семейство × грейд», не менее 127 различающихся экземпляров на пару; пять форматов частей, каждая часть оценивается 0/1 | `apps/api/src/domain/assessment/bank/`, `data/assessment-bank/README.md` |
| Условия попадания кандидата в поиск | Подтверждён email, заполнен профиль, есть подтверждённая квалификация, активное согласие на публикацию, включена видимость, поиск не «на паузе» и выбран хотя бы один заполненный канал для раскрытия контактов | `domain/candidate/discoverability.ts` |
| Раскрытие контактов | Принятие приглашения + явное подтверждение раскрытия; раскрываются только выбранные и заполненные каналы, только принявшей компании; отзыв доступа прекращает дальнейший показ (в JSON и PDF), но не «забирает» уже полученное | `InvitationsService`, `ContactAccessGrant`, `ProfilePresenter` |
| Повторное приглашение | У компании не более одного **активного** (`SENT`/`VIEWED`) приглашения кандидату; после финального статуса можно отправить новое | частичный уникальный индекс `Invitation_one_active_per_pair` |
| Вакансии и отклики (дополнительно по ТЗ) | Вакансия — публичная форма тех же структурированных требований с обязательной вилкой GROSS; отклик возможен при подтверждённой квалификации по специализации вакансии, заполненном профиле и канале раскрытия (публикация профиля не нужна); несоответствие грейду и навыкам отклик не блокирует, а помечается; отклик — явное согласие на раскрытие контактов **этой** компании; отзыв отклика доступ по умолчанию не закрывает (явный флажок); не более одного активного отклика на вакансию; сроков действия вакансии и лимитов откликов нет | `domain/applications/state.ts`, `VacanciesService`, `ApplicationsService`, индекс `Application_one_active_per_pair` |
| Подтверждение email | Обязательно: до него доступны только экран подтверждения, повторная отправка письма и выход. Ссылка одноразовая, действует 24 часа (`EMAIL_VERIFICATION_TTL_HOURS`); GET по ссылке ничего не подтверждает — нужен явный POST | `auth`, `.env` |
| Вход | Email и пароль (Argon2id), серверная сессия 7 суток; восстановление пароля и вход через ФСП ID **не реализованы** | `auth`, `SESSION_TTL_HOURS` |
| Хранение и удаление данных | Сроки хранения и удаление по запросу не реализованы; сохранённые подборки хранят снимок результатов без контактов | `SelectionRun` |
| Язык и устройства | Интерфейс только на русском; адаптивная вёрстка для телефона (проверена автоматически эмуляцией 390 и 320 px в Chromium; реальные устройства, Safari и Firefox не проверялись) | `apps/web`, E2E 9 |
| Резюме | Загружаемое PDF-резюме — источник **предложений** для профиля, а не подтверждения: распознавание по правилам без ML, только PDF с текстовым слоем, файл не хранится; навыки и грейд остаются самоописанием | `domain/resume`, `modules/resume` |
| Короткие задания | Не чаще одного задания в неделю на кандидата, срок ответа 7 дней, не более 10 активных заданий на компанию; задание подбирается по **подтверждённой** квалификации; результат — сигнал регулярности («решено за 90 дней»), он не меняет грейд и не входит в формулу подбора; опубликованное задание не редактируется | `domain/tasks`, `modules/tasks` |

## 3. Технические допущения

- Справочники специализаций, групп компетенций и навыков задаются в коде с версией и синхронизируются в БД при старте API; первичный ключ — стабильный код (`BACKEND`, `sql`), а не UUID.
- Ограничение частоты запросов хранится в памяти процесса API (один экземпляр MVP); при горизонтальном масштабировании нужен общий счётчик (например, в PostgreSQL или Redis).
- Ранжирование выполняется в backend после SQL-фильтрации — допустимо для синтетического объёма; ограничения масштабирования описаны в `docs/matching.md`.
- Внешние HTTP-запросы приложения во время работы отсутствуют (кроме SMTP).
- Ограничения на повторные приглашения после отказа или истечения нет (ограничен только один активный), как и на повторные отклики после отзыва: защита от навязчивых и фиктивных предложений и массовых откликов требует проверки компаний, лимитов и модерации — вне MVP.
- В контейнерах режим `NODE_ENV` фиксирован (`production`), адрес SMTP внутри сети задаётся `DOCKER_SMTP_HOST`/`DOCKER_SMTP_PORT`: значения `.env`, рассчитанные на запуск на хосте (`localhost`), в контейнеры не передаются.
- В production значение `SESSION_SECRET` из `.env.example` отвергается при старте; для Docker-запуска секрет нужно сгенерировать (`openssl rand -hex 32`).

## 4. Вопросы к организаторам (приоритетные)

Ответы на них могут изменить продукт; рабочие решения MVP — в таблице выше.

1. Допускается ли несколько подтверждённых специализаций у одного кандидата в интерфейсе и в поиске (в данных это уже возможно)?
2. Какие шкала грейдов, пороги прохождения и сроки пересдачи считаются допустимыми? Нужна ли внешняя калибровка тестов?
3. Должен ли тест быть общим или собираться под требования конкретного работодателя (в MVP — общий, с предпросмотром покрытия требований)?
4. Каков формат и порядок доступа к реестру ФСП (OIDC, API, поля, лимиты), кто владелец данных и на каком основании они показываются работодателям?
5. Какие тексты согласий и политик обработки персональных данных необходимы и какие сроки хранения и удаления данных применимы?
6. Как проверять компании и бороться с фиктивными предложениями (проверка юрлица, модерация, жалобы, лимиты приглашений)?
7. Нужны ли интеграция с ATS, несколько сотрудников в одной компании, мобильное приложение (адаптивная версия реализована), уведомления о новых заданиях и откликах?

## 5. Где менять решения

| Что менять | Где |
|---|---|
| Пороги, длительность, задержки пересдачи, навыки | новая версия политики в `apps/api/src/config/policies.ts`, выбор через `ASSESSMENT_POLICY_VERSION` |
| Веса формулы, вклад заявленного навыка, баллы ФСП | `MATCHING_FORMULAS`, `MATCHING_FORMULA_VERSION` |
| Срок действия приглашения | `INVITATION_POLICIES`, `INVITATION_POLICY_VERSION` |
| Тексты и версии согласий | `CONSENT_POLICY_VERSIONS` в `config/policies.ts` |
| Состав банка заданий | `apps/api/src/domain/assessment/bank/*` (новая версия семейства; затем `pnpm bank:manifest`, `pnpm validate:quality`) |
| Справочники специализаций, навыков, отраслей | `apps/api/src/domain/catalog/*` (синхронизируются в БД при старте) |
| Поля, видимые работодателю | `apps/api/src/domain/privacy/profile-view.ts` (и тест `privacy.int-spec.ts`) |
| Релевантность достижений ФСП | `apps/api/src/domain/matching/fsp-relevance.ts` |

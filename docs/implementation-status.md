## 1. Сводка

MVP готов к **технической демонстрации** на локальной машине: оба кабинета, обязательная механика тестирования и подбора, приглашения с
раскрытием контактов, четыре специализации × три грейда, синтетические данные, валидация качества, Docker Compose, OpenAPI и документация.
Это **не** готовый к промышленной эксплуатации продукт и **не** доказательство точности грейдинга (см. раздел 5).

## 3. Производительность

Ориентир ТЗ — десятки одновременных пользователей и приемлемое время основных операций; целевой показатель проекта — p95 до 1 секунды на 1000 синтетических
кандидатов и 20 параллельных пользователей (это цель, а не заранее достигнутый факт). Замер — `pnpm load:test` (`scripts/load-test.mjs`).

**Окружение:** production-образы Docker Compose на одной машине (Windows 11, Ryzen 7 3700X 8 ядер/16 потоков, 32 ГБ ОЗУ, Docker Desktop/WSL2), одна реплика API,
PostgreSQL 17 в контейнере. Нагрузку создают виртуальные пользователи **без пауз** (каждый сразу отправляет следующий запрос) с настоящими сессиями и CSRF;
защитные механизмы не отключались, поэтому сессий мало (4 работодателя и 3 кандидата), а параллелизм создают запросы. Смесь операций: банк, построение
подборки, сохранённая подборка, карточка с объяснением, PDF, профиль и допуск к тестам кандидата. 12–15 секунд на уровень.

### Выводы и ограничения

* Пропускная способность одной реплики API — около 50 запросов/с при 1000 кандидатов и около 100 при 114: стоимость ранжирования растёт с числом кандидатов специализации,
  так как оно выполняется в backend после SQL-фильтрации. Задержка растёт линейно с числом параллельных запросов (замкнутая нагрузка без пауз тяжелее реальной работы людей).
* Это единичный замер на одной машине на синтетических данных, а не нагрузочное тестирование промышленной системы; число сессий мало, поэтому проверяется в основном
  вычислительная часть, а не стоимость входа (Argon2id).
* Для роста нужны: несколько реплик API с общим счётчиком ограничения частоты, предрасчёт и индексы для подбора (в том числе по подтверждённым навыкам), кэширование справочников.
* Генерация тестов измерена отдельно в `validate:quality`: экземпляр задания — 0,05–0,4 мс, попытка из 6 экземпляров — 0,4–1,0 мс (`validation-results.md`, раздел 2.2 и 2.8).

## 4. Экспорт документации (PDF/DOCX)

`pnpm docs:export` (скрипт `scripts/export-docs.mjs`) выполняет экспорт OpenAPI и формирует из `docs/submission.md` файлы в `docs/export/`:
**PDF** (Markdown → HTML → печать в Chromium; кириллица, таблицы, код, встроенный шрифт JetBrains Mono) и **DOCX** (библиотека `docx`: заголовки, списки,
таблицы, код, цитаты). Скрипт сам проверяет результат: в PDF — наличие кириллического текста (не менее 85 % символов источника), заголовков и отсутствие символов
замены; в DOCX — совпадение числа заголовков и таблиц с источником. Результат последнего запуска — в разделе «Проверка экспорта» ниже.

Для экспорта нужен браузер Chromium Playwright (`pnpm --filter @fsp/e2e install-browsers`); без него PDF не создаётся, скрипт сообщает причину и завершается с ошибкой.

## 5. Известные ограничения

**Качество и валидация**
* Пороги прохождения (75/50/90/75), сроки (30 дней на повтор уровня, 90 дней)  и состав банка — рабочие допущения, не откалиброванные на реальных людях. Валидация выполнена на
  синтетических данных с авторской разметкой; она подтверждает корректность и воспроизводимость генерации и оценки, но **не доказывает, что тест измеряет реальную квалификацию**.
* Подбор: разница с baseline по Precision@5 (+0,025, 95 %-интервал [−0,100; 0,150]) статистически не значима при 8 итоговых потребностях; основное преимущество — жёсткие условия.
* Банк небольшой (24 семейства): темы повторяются между попытками одного кандидата; различаются условия.

**Функциональность (вне MVP, не выдаётся за готовое)**
* Не реализованы: проверка компаний и защита от фиктивных предложений, интеграция с ATS, несколько сотрудников в компании, восстановление пароля, удаление данных по запросу, OCR сканов резюме, уведомления о заданиях и откликах.
* Тест общий для специализации и грейда; обязательные экзамены под конкретную вакансию не реализованы (есть предпросмотр покрытия требований).
* Ограничения на повторные приглашения после отказа и на повторные отклики после отзыва нет (ограничен только один активный).

**Интеграции и эксплуатация**
* ФСП — только `MockFspProvider` с синтетической фикстурой; реального API, OIDC/Keycloak и согласованного контракта нет. Коды привязки одноразовые.
* Ограничение частоты запросов хранится в памяти одного процесса API (несколько экземпляров требуют общего счётчика); по умолчанию 10 регистраций в час с адреса.
* Ранжирование выполняется в backend после SQL-фильтрации — достаточно для синтетического объёма.
* Нет централизованного журналирования, метрик и алертинга; резервное копирование БД не настроено.

**Правовые и организационные**
* Согласие и ролевой доступ не доказывают соответствие 152-ФЗ; тексты согласий — рабочие формулировки без юридической проверки; срок хранения и удаление данных не реализованы.
* Лицензия на код проекта владельцем не выбрана; зависимости — открытые лицензии (исключения перечислены в submission).

**Ограничения проверок**
* Браузерные тесты выполнены только в Chromium (десктоп 1440×900; телефон — эмуляция 390 и 320 px); кроссбраузерность и реальные мобильные устройства не проверялись.
* Docker-запуск проверен на машине разработки с уже загруженными базовыми образами; полностью «чистая машина» (новый клон репозитория, пустые кэши) не воспроизводилась.
  Сборка образов требует доступа к реестрам npm и Debian.
* Нагрузочный замер — единичный, на одной машине.

| F4 | разметка подбора | на выборке tuning слабая различимость вариантов весов (всё 1,0) | зафиксировано как ограничение набора; веса не подбирались по разметке |
| F5 | распознавание резюме · парсер | первый прогон на независимом ручном наборе и синтетической выборке: не распознавались английские названия городов, «Фамилия Имя, должность» как ФИО, периоды «по н.в.» и «с 2018 года по настоящее время» (доля стажа в пределах ±12 мес. на синтетике — 73 %); часть разметки генератора не соответствовала тексту | парсер доработан общими правилами, разметка генератора привязана к реально выведенному тексту; **ручной набор после правок уже не «невиданный»**, оставшееся расхождение (ФИО в строке «Контакты: …») не подгонялось и показано в отчёте |
| F6 | определение грейда · симуляция test-retest | при сдвиге трудности банка на ±0,5 пороги качества определения грейда нарушаются: при труднее — больше кандидатов без грейда, при легче — завышение выше 5 % | пороги и модель не подгонялись; зависимость зафиксирована как ограничение, калибровка — после пилота на реальных кандидатах |

Также в ходе сквозных проверок исправлены: гонка двойного клика по согласию на публикацию (частичный уникальный индекс, миграция `*_consent_single_active`),
порядок записей истории приглашения при совпадении меток времени, текст уведомления «профиль опубликован», когда профиль фактически не виден (не выбран канал связи),
запуск Docker-контейнеров с настройками хоста из `.env` (адрес SMTP, `NODE_ENV`) и версия движка миграций Prisma в образе API, а также неиспользуемая зависимость `@nestjs/throttler`;
постоянная «неготовность» API (`/health/ready` = 503), если PostgreSQL ещё не принимал соединения в момент старта (теперь синхронизация справочников повторяется с задержкой и проверяется самой пробой готовности; unit-тест `catalog-sync.service.spec.ts`);
невозможность сохранить неполный профиль и потеря ответов опроса при перезагрузке (требование «храни прогресс»: теперь профиль сохраняется частично, а блок «Для попадания в поиск» показывает, чего не хватает; черновик опроса хранится в браузере; проверено сквозным сценарием 1).

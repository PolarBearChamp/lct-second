# Подбор кандидатов

Платформа строит подборку **по описанию потребности**, а не по вакансии: работодатель задаёт требования, платформа
находит кандидатов с подтверждённой тестом квалификацией и объясняет каждый результат. Формула — `matching-formula-v1`,
алгоритм — `rank-v1` (`apps/api/src/domain/matching/rank.ts`).

## 1. Потребность работодателя

| Поле | Смысл |
|---|---|
| Специализация | одна из четырёх; кандидат должен иметь **подтверждённую** квалификацию именно по ней |
| Допустимые грейды | подмножество Junior / Middle / Senior; сравнивается грейд, **подтверждённый тестом** |
| Обязательные навыки | жёсткое условие: навык должен быть подтверждён тестом (≥ 2 кейса, результат ≥ 70). Если для навыка нет проверяющих заданий, потребность не создаётся (`422`): нельзя поставить условие, которое никто не сможет выполнить |
| Желательные навыки | дают баллы; режим каждого — `VERIFIED_ONLY` (только подтверждённый тестом) или `SELF_REPORTED_ALLOWED` (заявленный кандидатом засчитывается частично) |
| Формат работы и город | `REMOTE`, `HYBRID`, `OFFICE`; город сравнивается, если формат не удалённый |
| Зарплатная вилка | обязательна, рубли в месяц **до вычета налогов (GROSS)** |

Изменение потребности создаёт новую версию (`HiringNeed.version`); подборка запоминает версию и снимок требований, по которым построена.

## 2. Кто вообще виден в подборке

Кандидат участвует в подборе, только если выполнены **все** условия (`domain/candidate/discoverability.ts`): email подтверждён, профиль
заполнен, дано активное согласие на публикацию, включена видимость в поиске, готовность «рассматриваю предложения» (не «на паузе»),
есть подтверждённая квалификация, выбран хотя бы один канал связи для раскрытия после принятия приглашения. Интерфейс кандидата
показывает, чего именно не хватает. Скрытый или снявший согласие кандидат исчезает и из новых, и из **сохранённых** подборок и закладок.

## 3. Жёсткие условия

Проверяются до формулы (`mandatoryViolations`). Кандидат, нарушивший любое из них, в выдачу не попадает — **ни бонус ФСП, ни высокий
балл, ни самоописание не компенсируют провал обязательного условия**.

| Условие | Причина отклонения |
|---|---|
| Видимость кандидата (раздел 2) | `NOT_DISCOVERABLE` |
| Подтверждённая специализация совпадает с потребностью | `SPECIALIZATION` |
| Подтверждённый грейд входит в допустимые | `GRADE` |
| Все обязательные навыки подтверждены тестом | `REQUIRED_SKILL` |
| Формат работы потребности входит в форматы кандидата | `WORK_FORMAT` |
| Для не удалённой работы совпадает город | `CITY` |
| Вилки зарплат пересекаются — **если** ожидания заданы и кандидат их не скрыл | `SALARY` |

Ожидания «не указаны» или «скрыты кандидатом» не отсекают и не используются в подборе — объяснение прямо это пишет.
Работодатель может **сузить** выдачу уточнениями (только с достижениями ФСП, минимальный балл теста, дополнительные обязательные навыки,
города); уточнения никогда не ослабляют обязательные условия и сохраняются как дочерняя подборка (`parentRunId`).

Число отклонённых по каждой причине (и по каждому неподтверждённому обязательному навыку) сохраняется в подборке. Если не прошёл
никто, экран подборки показывает причины отсева, например «не подтверждён навык «PostgreSQL»: 14». Условия **не ослабляются
автоматически**: работодатель сам решает, изменить ли потребность. Отдельный экран «Тест под требования» показывает, какими заданиями
банка покрыты требования потребности (покрыто / частично / не покрыто).

## 4. Формула

```
score = 70 · preferredFit + 25 · assessmentQuality + 5 · fspEvidence      (компоненты 0…1, итог 0…100, округление до 0,01)
```

| Компонент | Расчёт |
|---|---|
| `preferredFit` | среднее по желательным навыкам: подтверждён тестом — 1; заявлен кандидатом и режим `SELF_REPORTED_ALLOWED` — **0,3**; иначе 0. Желательных навыков нет — 1 |
| `assessmentQuality` | общий балл теста / 100 |
| `fspEvidence` | `min(Σ баллов / 6, 1)`: за **релевантное** специализации достижение ФСП — участие 1, призёр 2, победа 3; по одному мероприятию учитывается сильнейшая запись |

Релевантность достижения определяется справочником `fsp-relevance-v1`: дисциплина задаёт круг специализаций, роль в команде сужает его
(например, достижение по робототехнике не релевантно Frontend). Веса `70/25/5` и вклад заявленного навыка 0,3 заданы в
`config/policies.ts` и **не подбирались по разметке валидации**. Это относительная мера соответствия описанной потребности, а **не
вероятность найма или процент пригодности**.

**Стабильный порядок:** `score ↓`, затем балл теста `↓`, затем `id` кандидата `↑`. Сортируется всё множество, и только потом применяется
пагинация, поэтому порядок не зависит от размера страницы (проверяется тестом).

**Общий банк кандидатов** (экран «Банк») использует те же видимость и приватность и фильтры (специализация, грейд, категория
«специализация:грейд», навыки — только подтверждённые или любые, формат работы, город, наличие достижений ФСП); сортировка — `95·assessmentQuality + 5·fspEvidence`
(`bankWeights`).

## 5. Объяснение

Каждый результат содержит структурированное объяснение (`MatchExplanation`): «Почему подходит», «Что пока не подтверждено»,
пройденные условия, совпавшие и не совпавшие желательные навыки (с типом свидетельства `VERIFIED` / `SELF_REPORTED`), статус зарплаты и
разложение итога по компонентам. Пример из демо-данных (кандидат без раскрытых контактов; потребность «Backend-разработчик в команду
платежей», Middle/Senior, обязательные SQL и PostgreSQL):

> **Почему подходит**
> * Грейд по результатам тестирования Middle входит в допустимые (Middle, Senior)
> * Подтверждены тестом все обязательные навыки: SQL, PostgreSQL
> * Подходит формат работы: удалённо
> * Ожидания 230 000–295 000 ₽ пересекаются с вилкой 250 000–350 000 ₽
> * Желательные навыки указаны кандидатом (вклад ×0.3): Apache Kafka
> * Общий балл теста: 100 из 100
> * Релевантные достижения ФСП: 2 мероприятие(й), 4 балл(ов) бонуса
>
> **Что пока не подтверждено**
> * Apache Kafka: только самоописание, тестом не проверялся
>
> Вклад в оценку соответствия 49.3 / 100 — желательные навыки 0.30 × 70 = 21.0; качество теста 1.00 × 25 = 25.0; бонус ФСП 0.67 × 5 = 3.3

Кандидат **без ФСП** получает ту же карточку с честной пометкой «Нет релевантных достижений ФСП (это не снижает доступ к подборке)»:
отсутствие истории не отсекает и не помечает его как худшего по доступу (проверено сквозным сценарием 5).

## 6. Сохранённые подборки

`SelectionRun` хранит снимок потребности и её версию, фильтры, версию и параметры формулы, число рассмотренных/подошедших, сводку
причин отклонения, длительность и результаты (место, балл, компоненты, объяснение). **Контакты в снимок не попадают.** При открытии
сохранённой подборки доступ к каждому кандидату проверяется заново: скрытый кандидат заменяется заглушкой «Кандидат недоступен:
профиль скрыт или больше не опубликован» (место в списке сохраняется, детали не показываются), а карточки остальных строятся презентером
с текущими правами компании, поэтому раскрытие или отзыв доступа отражается сразу.

### Отклики на вакансию: то же правило

Для откликнувшихся кандидатов соответствие вакансии считается **той же функцией** (`mandatoryViolations` + `rankForNeed`) по требованиям вакансии: подходящие получают оценку и объяснение, у остальных перечисляются невыполненные обязательные условия. Отличия от подбора: видимость в поиске не проверяется (кандидат откликнулся сам и раскрылся этой компании), а несоответствие не отсекает отклик — оно показывается и кандидату до отклика, и работодателю. Список откликов по умолчанию сортируется «подходящие выше → оценка → балл теста → дата».

## 7. Baseline и проверка качества

Для сравнения принят baseline из ТЗ: те же кандидаты, отфильтрованные только по специализации и допустимому грейду и отсортированные по
баллу теста. Сравнение выполняет `pnpm validate:quality` на размеченных синтетических данных (12 потребностей, 76 кандидатов,
228 размеченных пар; 4 потребности — отладка, 8 — итоговая выборка). Итог по финальной выборке
(полный отчёт и интервалы — [validation-results.md](validation-results.md)):

| Система | Precision@5 | nDCG@5 | Нарушения явных условий в top-5 |
|---|---|---|---|
| `matching-formula-v1` | 0,68 | 0,921 | 0,0 % (0 из 8 потребностей) |
| baseline (специализация/грейд + балл теста) | 0,65 | 0,833 | 36,1 % (7 из 8 потребностей) |

Как это читать: основное превосходство над baseline дают **жёсткие условия** (формат, зарплатная вилка, подтверждённые обязательные
навыки), которых в baseline нет; разница по Precision@5 (+0,025) статистически не значима (95 %-интервал [−0,100; 0,150] при 8
потребностях). Разметка авторская и синтетическая; формула намеренно строгая и теряет часть «допустимых» кандидатов (5 из 34 в
финальной выборке) — это следствие правил ТЗ, а не ошибка. Метрики не доказывают качество подбора на реальных данных.

## 8. Ограничения

* Ранжирование выполняется в backend после SQL-фильтрации — подходит для синтетического объёма MVP; для десятков тысяч кандидатов
  потребуются индексы, предрасчёт и поиск по навыкам в БД (GIN-индекс по подтверждённым навыкам уже есть).
* Нет обратной связи по найму (кто принят и работает) и обучения на ней: статусы приглашений и откликов не влияют на формулу, она фиксирована и версионируема.
* Подбор ограничен навыками, которые проверяются заданиями банка; навык без проверяющих заданий нельзя сделать обязательным.
* Релевантность ФСП определяется простым справочником «дисциплина → специализации (→ роль)».

## Кандидаты без подтверждённого грейда

По рекомендации организаторов (встреча организаторов с участниками, вопросы 6 и 20) кандидат с опубликованным профилем, но без подтверждённого грейда по специализации потребности, **не скрывается**, а показывается **отдельным блоком после всех подтверждённых**:

* условия потребности проверяются по заявленным данным: заявленный грейд в допустимых, обязательные навыки указаны кандидатом, формат, город, пересечение вилок; уточнения «минимальный балл» и «дополнительные подтверждённые навыки» такие кандидаты не проходят;
* балл подбора не считается (формула опирается на результат теста); порядок внутри блока — желательные навыки из самоописания ↓, бонус ФСП ↓, идентификатор ↑;
* в объяснении первым пунктом «Что пока не подтверждено» стоит «Грейд не подтверждён тестом…»; в интерфейсе — пометка и отдельный заголовок блока;
* в общем банке они — последняя «категория» своей специализации (`SPEC:UNCONFIRMED`), фильтр «Показывать без подтверждённого грейда» скрывает их.

Подтверждённый блок и его метрики не зависят от неподтверждённых (проверено unit-тестом и повторным `validate:quality`: P@5 и nDCG@5 не изменились).

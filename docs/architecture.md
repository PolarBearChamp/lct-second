# Архитектура

Документ описывает, как устроена платформа, где в коде находятся ключевые решения и какие инварианты гарантирует база данных.
Решения, принятые командой без указаний в ТЗ, перечислены в [assumptions.md](assumptions.md).

## 1. Компоненты

```text
 Браузер ──HTTP──▶ web (Next.js 16, App Router, :3000)
                     │  rewrites: /api/v1/* ─▶ API_INTERNAL_URL
                     ▼
                   api (NestJS 11, :3001, префикс /api/v1) ──SMTP──▶ Mailpit (локально) / внешний SMTP
                     │  Prisma 7 + adapter-pg
                     ▼
                   PostgreSQL 17 (volume, healthcheck)
                   MockFspProvider ◀── data/fixtures/fsp-mock.json (синтетический реестр)
```

* **web** — единственная точка входа для браузера. Запросы к `/api/v1/*` проксируются во внутренний API, поэтому cookie и CSRF
  работают в одном origin. Серверные компоненты читают `API_INTERNAL_URL` во время работы; адрес прокси «запекается» в сборку
  (в Docker передаётся build-аргументом).
* **api** — модульный монолит: один процесс, независимые модули, чистая доменная логика отдельно от Nest и БД.
* **PostgreSQL** — единственное хранилище состояния (сессии, попытки, подборки, приглашения). Ограничения целостности
  заданы схемой и явной SQL-миграцией, а не только кодом.
* **Почта** — SMTP; локально Mailpit (интерфейс на `127.0.0.1:8025`, наружу не публикуется).
* **ФСП** — интерфейс `FspProvider`; в MVP реализован только `MockFspProvider` (см. [fsp-integration.md](fsp-integration.md)).
* Внешних HTTP-вызовов во время работы нет, кроме SMTP. Внешние AI/LLM API не используются.

## 3. Модули API

| Модуль | Ответственность |
|---|---|
| `auth` | Регистрация, вход, подтверждение email, серверные сессии, CSRF, Argon2id, ограничение частоты |
| `users` | `GET /auth/me`: пользователь, роль, состояние онбординга |
| `catalogs` | Специализации, группы компетенций, навыки, справочники, опрос; синхронизация справочников в БД при старте |
| `candidate-profiles` | Профиль, опрос, согласия (с историей), условия попадания в поиск, квалификации и их история |
| `assessments` | Старт, автосохранение, отправка, прерывание, истечение попытки; выдача квалификации; допуск к повтору |
| `companies`, `hiring-needs` | Компания работодателя, потребности (версионирование при изменении), план теста под требования |
| `matching` | Подбор по потребности, общий банк, сохранённые подборки, закладки |
| `invitations` | Приглашения, атомарные переходы статусов, доступ к контактам и его отзыв |
| `vacancies` | Вакансии работодателя (публикация, закрытие, версии), общий список для кандидата, самостоятельные отклики, работа с откликами, оценка соответствия тем же правилом подбора |
| `resume` | `POST /candidate/profile/resume`: PDF (до 5 МБ) → текст в изолированном дочернем процессе (лимиты страниц, символов, времени, памяти) → предложения для профиля; файл нигде не сохраняется |
| `tasks` | Короткие задания работодателя (черновик → активно → закрыто), ленивое предложение кандидатам не чаще раза в неделю, ответы, автоматическая проверка теста, оценка разбора автором |
| `companies` (проверка) | Добровольная проверка компании (метка доверия): ИНН, демонстрационный реестр `data/fixtures/company-registry-mock.json`, название, домен почты аккаунта |
| `fsp` | Привязка ФСП ID по одноразовому коду, синхронизация, отвязка |
| `profile-view`, `profile-pdf` | Единый презентер профиля (JSON) и PDF по тому же представлению |
| `audit`, `mail`, `health` | Журнал значимых событий без персональных данных, письма, `live`/`ready` |

Сквозные части (`src/common`): единый формат ошибок `{ code, message, details?, requestId }`, идентификатор запроса,
валидация UUID, часы (`Clock` — подменяемы в тестах), ограничитель частоты, сервис версионируемых политик.

## 4. Доменная логика без Nest и БД (`src/domain`)

| Пакет | Что внутри |
|---|---|
| `assessment` | Банк семейств заданий (`bank/*`), детерминированный генератор (`rng.ts`, sfc32), построение плана теста (`blueprint.ts`), создание экземпляра с разделением публичной и закрытой частей (`instantiate.ts`), оценка (`evaluate.ts`), подсчёт баллов (`scoring.ts`), допуск к попытке (`eligibility.ts`), ручные контрольные примеры (`controls.ts`) |
| `matching` | Жёсткие фильтры, формула, объяснения, стабильная сортировка (`rank.ts`); релевантность ФСП (`fsp-relevance.ts`) |
| `privacy` | `profile-view.ts` — единственное место, где решается, какие поля профиля видит владелец, работодатель без доступа и работодатель с доступом |
| `invitations` | Конечный автомат статусов и порядок истории (`state.ts`) |
| `applications` | Автомат статусов отклика и вакансии, допуск к отклику (`state.ts`) |
| `resume` | Разбор текста резюме по правилам и словарям справочников (`parse.ts`): контакты, ФИО, город, навыки, стаж, специализация, предположение о грейде; без ML |
| `tasks` | Содержимое задания, подбор по подтверждённой квалификации, период предложения, срок ответа (`rules.ts`) |
| `companies` | Проверка ИНН, сопоставление названия и домена почты (`verification.ts`) |
| `candidate/age` | Возрастные группы (до 16, 16–17, взрослый) для правил публикации и приглашений (`age.ts`) |
| `candidate` | Условия попадания в поиск (`discoverability.ts`) |
| `catalog` | Справочники специализаций, групп, навыков, ролей и т. д. |

Чистые функции покрыты unit-тестами и используются одинаково в API, в `seed` и в `validate:quality`, поэтому показатели
валидации считаются тем же кодом, что работает в приложении.

## 5. Модель данных

Идентификаторы — UUID, время — `timestamptz` (UTC), зарплата — целые рубли в месяц (GROSS), опыт — месяцы.

| Группа | Таблицы |
|---|---|
| Доступ | `User`, `Session` (хранится SHA-256 хеш токена), `EmailVerificationToken`, `ConsentRecord` |
| Справочники | `Specialization`, `CompetencyGroup`, `Skill` (первичный ключ — стабильный код, например `BACKEND`, `sql`) |
| Кандидат | `CandidateProfile`, `CandidateSkill`, `CandidateQualification` (одна на пару кандидат+специализация), `QualificationHistory` (неизменяемая история) |
| Тестирование | `AssessmentAttempt`, `AssessmentItem` (снимок экземпляра: публичная часть + закрытый ключ), `AssessmentAnswer` (ревизии автосохранения) |
| Работодатель | `Company`, `HiringNeed` (версия требований), `SelectionRun` + `SelectionResult` (снимок подборки), `CandidateBookmark` |
| Приглашения | `Invitation`, `InvitationEvent` (история статусов), `ContactAccessGrant` |
| Вакансии и отклики | `Vacancy`, `Application` (снимок вакансии), `ApplicationEvent`; доступ к контактам при отклике — тот же `ContactAccessGrant` |
| Короткие задания | `ShortTask` (условие и закрытый верный вариант), `TaskAssignment` (предложение кандидату, ответ, оценка) |
| Возраст и метка доверия | `CandidateProfile.birthDate`, `guardianName`, согласие `GUARDIAN_CONSENT`; `Company.inn`, `verificationStatus`, `verificationChecks` |
| ФСП | `FspLink` (состояние: `LINKED_WITH_HISTORY`, `LINKED_WITHOUT_HISTORY`, `SYNC_ERROR`), `FspAchievement`, `FspLinkCodeRedemption` (одноразовость кода) |
| Аудит | `AuditEvent` |

### Инварианты на уровне БД

Выражены явной SQL-миграцией (`prisma/migrations/*_partial_unique_indexes`, `*_consent_single_active`) — Prisma их описать не может:

| Инвариант | Механизм |
|---|---|
| У кандидата не более одной активной попытки | частичный уникальный индекс `AssessmentAttempt(candidateId) WHERE status = 'IN_PROGRESS'` |
| Не более одного активного отклика кандидата на вакансию | частичный уникальный индекс `Application(vacancyId, candidateId) WHERE status IN ('SENT','VIEWED','SHORTLISTED')` |
| Доступ к контактам выдан приглашением или откликом | `CHECK` на `ContactAccessGrant`: заполнен `sourceInvitationId` или `sourceApplicationId` |
| Не более одного неотвеченного задания у кандидата | частичный уникальный индекс `TaskAssignment(candidateId) WHERE status = 'OFFERED'` (параллельные открытия раздела дают одно предложение) |
| Задание не предлагается кандидату повторно | уникальность `TaskAssignment(taskId, candidateId)` |
| Корректное содержимое задания и ответа | `CHECK`: у теста 2–6 вариантов и верный индекс внутри диапазона, у разбора вариантов нет; ответ задан ровно у отправленных заданий |
| Адресное задание знает отправителя; «одно неотвеченное» — только для регулярных | `CHECK (source <> 'DIRECT' OR assignedByUserId IS NOT NULL)`; частичный индекс `… WHERE status = 'OFFERED' AND source = 'ROTATION'` |
| Балл в подборке — ровно у кандидатов с подтверждённым грейдом | `CHECK` на `SelectionResult (gradeConfirmed, score)` |
| ИНН — 10 или 12 цифр | `CHECK` на `Company.inn` |
| Не более одного активного приглашения от компании кандидату | частичный уникальный индекс `Invitation(companyId, candidateId) WHERE status IN ('SENT','VIEWED')` |
| Не более одного действующего согласия каждого типа | частичный уникальный индекс `ConsentRecord(userId, type) WHERE withdrawnAt IS NULL` |
| Корректные зарплатные вилки | `CHECK` для потребности, приглашения, профиля; опыт ≥ 0; ревизия ответа ≥ 1 |
| Фильтр по подтверждённым навыкам | GIN-индекс `CandidateQualification(verifiedSkills)` |

Переходы статусов выполняются условным `UPDATE … WHERE status IN (…)` с проверкой числа затронутых строк: из двух
конкурентных `accept`/`withdraw` выигрывает ровно один, второй получает `409`.

## 6. Ключевые потоки

### Регистрация и доступ

`register` → письмо с одноразовой ссылкой → `verify-email` (GET безопасен: подтверждает только явный POST по кнопке) → вход →
серверная сессия в `HttpOnly` cookie (`SameSite=Lax`, `Secure` в production). Изменяющие запросы требуют CSRF-токен
(`X-CSRF-Token`, подписанный double-submit) и проверку `Origin`; `CsrfGuard` выполняется раньше `AuthGuard`. До подтверждения email
доступны только экран подтверждения, повторная отправка письма и выход.

### Тестирование

Допуск (`eligibility`) → план теста (`blueprint`: по два мини-кейса из каждой из трёх групп, семейства не повторяются) →
экземпляры из (семейство, версия, грейд, seed) → снимок в `AssessmentItem` (публичная часть и закрытый ключ хранятся раздельно) →
автосохранение ответов с ревизией (устаревший autosave отклоняется) → `submit` с финальными ответами либо серверное истечение по
таймеру → оценка и выдача квалификации в одной транзакции. Подробности: [assessment.md](assessment.md).

### Подбор

Потребность (обязательные навыки с проверяющими заданиями, допустимые грейды, формат, зарплатная вилка) → SQL-выборка видимых
кандидатов → жёсткие фильтры и формула в `rank.ts` → стабильная сортировка всего множества и только потом пагинация →
сохранённый `SelectionRun` со снимком результата и объяснений. Подробности: [matching.md](matching.md).

### Приглашение и раскрытие контактов

Работодатель отправляет приглашение (вилка GROSS обязательна, `Idempotency-Key`, срок 14 дней) → кандидат видит зарплату и условия,
а также список данных, которые будут раскрыты → `accept` создаёт `ContactAccessGrant` для этой компании и раскрывает только выбранные
каналы связи → отзыв доступа немедленно прекращает показ в JSON и PDF. Подробности: [privacy.md](privacy.md).

### Вакансия и самостоятельный отклик

Работодатель создаёт вакансию (вилка GROSS обязательна) и публикует её → кандидат видит её в общем списке с зарплатой → `POST /candidate/vacancies/{id}/applications` с `confirmDisclosure`: в одной транзакции создаются отклик со снимком вакансии, запись в истории и `ContactAccessGrant` для этой компании (выбранные каналы) → работодатель видит отклик с оценкой соответствия (`rank-v1`, те же жёсткие условия, что в подборе; для откликнувшегося видимость в поиске не требуется) и работает с ним (`view`/`shortlist`/`reject`); кандидат отзывает отклик (по желанию вместе с доступом). Подробности: [submission.md](submission.md), раздел 6.6, и [privacy.md](privacy.md).

## 7. Безопасность и надёжность (кратко)

* Закрытые ключи заданий не покидают сервер: публичная часть формируется отдельным презентером, `packages/contracts` их не содержит.
* DTO профиля собираются из явного списка разрешённых полей, а не фильтрацией ORM-объекта: новое поле БД не попадёт наружу случайно.
* Пароли — Argon2id (`m=19456 KiB, t=2, p=1`); токены сессий и подтверждения хранятся только в виде хеша.
* Ответы API содержат `Cache-Control: private, no-store`; логи запросов без тел, cookie и персональных данных.
* Ограничение частоты входа, регистрации, повторной отправки писем, проверки токена и привязки ФСП — **в памяти процесса API**
  (достаточно для одного экземпляра; для нескольких нужен общий счётчик).
* Конфигурация окружения проверяется при старте; в production значение `SESSION_SECRET` из `.env.example` отвергается.

## 8. Развитие

Не реализовано и не выдаётся за готовое (подробнее в [implementation-status.md](implementation-status.md)): проверка компаний и борьба с
фиктивными предложениями, интеграция с ATS, распознавание сканов резюме (OCR), уведомления о заданиях и откликах, проверка на реальных устройствах, несколько
сотрудников одной компании, общий (распределённый) счётчик ограничения частоты, настоящая интеграция с ФСП ID (OIDC).

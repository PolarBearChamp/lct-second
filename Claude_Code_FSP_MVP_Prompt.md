# Промпт для Claude Code: платформа подбора ИТ-специалистов ФСП

Ты — ведущий fullstack-разработчик. Реализуй работающий MVP веб-платформы для обратного подбора ИТ-специалистов. Работодатель ищет кандидатов с подтверждёнными навыками и первым направляет предложение с зарплатой. Кандидат решает, раскрывать ли ему контакты.

Это задание на реализацию: нужны код, база данных, работающий интерфейс, тесты ключевой логики, демонстрационные данные и документация. Не заканчивай работу только планом, архитектурой или набором экранов с моками.

## 1. Контекст, приоритеты и порядок работы

Проект создают два fullstack-разработчика для хакатона. Срок пока не зафиксирован. Не придумывай дедлайн и не сокращай обязательный объём молча. Раздели работу на последовательные проверяемые этапы.

Подтверждённые пользователем решения:

- Frontend: Next.js.
- Backend: NestJS.
- База данных: PostgreSQL.
- Четыре специализации: frontend-разработчик, backend-разработчик, ML-инженер, manual QA.
- На этом этапе не использовать внешние AI/LLM API. Локальная модель также не должна быть обязательной зависимостью.
- Все демонстрационные и оценочные данные — собственная синтетика.
- Заявленный грейд отделён от подтверждённого.
- До успешного тестирования кандидат не попадает в основную выдачу.
- Достижения ФСП — дополнительное преимущество, не замена соответствию требованиям.

Это самостоятельная платформа, а не парсер сторонних вакансий. Главный сценарий: регистрация кандидата → опрос → тестирование → подтверждённая категория → подбор работодателем → приглашение с зарплатой → принятие → раскрытие контактов только этой компании.

Приоритеты конкурса: механика подбора — 35%, тестирование и валидация — 25%, интерфейс — 10%, техническая реализация — 7%, полнота и документация — 6%, дополнительные функции — 7%, презентация — 10%. Сначала обеспечь основной сценарий и качество оценки, затем дополнительные возможности.

Перед реализацией:

1. Изучи текущий репозиторий, README и применимые инструкции. Сохрани существующую работу. Если репозиторий пустой — создай проект.
2. Сформируй короткий план и `docs/implementation-status.md` с этапами и текущим состоянием.
3. Запиши принятые здесь допущения в `docs/assumptions.md`. Они ещё не согласованы с организаторами; не представляй их как требования исходного ТЗ.
4. Выбирай обычные технические детали самостоятельно, совместимо с существующим проектом. Не останавливай работу из-за косметических решений или несущественного выбора библиотек.
5. Если существенное требование невозможно выполнить, явно опиши причину и уже реализованный объём. Не имитируй готовность.
6. Сначала доведи один вертикальный сценарий до работы, затем распространи его на все четыре специализации. Финальный MVP должен поддерживать все четыре.

## 2. Границы MVP

Обязательно реализовать:

- Регистрацию, подтверждение email, вход, выход и две роли.
- Профиль кандидата с ручным вводом данных, опросом и настройками приватности.
- Генерацию стандартизированного PDF-профиля.
- Тестирование на Junior / Middle / Senior по каждой из четырёх специализаций.
- Генерацию вариантов заданий из версионируемого банка, серверную оценку, историю результатов и ограничения пересдач.
- Категоризацию по подтверждённым результатам.
- Профиль компании и описание потребности в специалисте.
- Поиск, фильтры, ранжирование и понятное объяснение соответствия кандидата.
- Приглашения с обязательной зарплатной вилкой, статусами, принятием и отказом.
- Серверный контроль доступа к контактам, включая PDF.
- Привязку к демонстрационному ФСП ID через сменный адаптер, достижения и работу без истории ФСП.
- Синтетические данные, воспроизводимую оценку качества, сквозные проверки.
- OpenAPI, инструкции запуска, Docker Compose и документацию для сдачи.

Отложить до завершения обязательного MVP:

- Публикацию вакансий в открытой ленте и самостоятельные отклики.
- Регулярные задания работодателей.
- Распознавание загруженных PDF-резюме.
- Чаты, видеозвонки, push-уведомления и WebSocket.
- Реальную интеграцию ФСП, Keycloak, ATS.
- Верификацию компаний и модерацию вакансий.
- Прокторинг, исполнение произвольного пользовательского кода.
- Векторную базу, embeddings, обучение ML-моделей, внешние LLM.
- Административную панель, платежи и монетизацию.

Для отложенных функций оставь понятные точки расширения в документации, не строй пустые сервисы и не добавляй неработающие кнопки.

## 3. Техническая архитектура

Используй модульный монолит NestJS и отдельный Next.js frontend в монорепозитории. Не вводи микросервисы, Kafka, RabbitMQ, Redis или Elasticsearch без конкретной доказанной необходимости.

Предлагаемая структура:

```text
apps/web                 Next.js, App Router, TypeScript
apps/api                 NestJS, REST API, Swagger
packages/contracts       безопасные общие типы/сгенерированный API-клиент
packages/config          общие настройки TypeScript и линтинга
data/assessment-bank     серверные определения заданий и версий
data/fixtures            синтетические исходные данные
data/validation          отдельные сценарии оценки и разметка
scripts                  seed, валидация, экспорт документации
docs                     архитектура, решения, API, результаты, демо
```

Для нового проекта по умолчанию: pnpm workspaces, Prisma и миграции, Tailwind CSS, доступные UI-компоненты, React Hook Form для сложных форм. Можно использовать TanStack Query для клиентского состояния запросов. Если в существующем проекте уже есть подходящие аналоги, не мигрируй ради этого списка.

Версии зависимостей выбирай совместимые на момент реализации, фиксируй lockfile и поддерживаемую версию Node.js. Не используй плавающие `latest` в итоговых инструкциях и Docker-образах. Не копируй API библиотек из памяти, если они не соответствуют установленной версии.

Backend-модули: Auth, Users, CandidateProfiles, Companies, Catalogs, Assessments, Matching, Invitations, FspIntegration, ProfilePdf, Audit, Health.

Браузер обращается к `/api/v1` на том же origin, что и Next.js. Настрой проксирование на NestJS. Для серверных запросов Next.js используй внутренний URL API и явно передавай cookie текущего запроса. Приватные ответы не кэшируй между пользователями. Доступ к PostgreSQL выполняется только из backend.

Не включай эталонные ответы, генераторы правильных ответов, скрытые параметры и seed заданий в frontend bundle или общий пакет.

## 4. Рабочие допущения до ответа организаторов

Следующие значения — выбранная реализация MVP, а не утверждение о правилах конкурса:

| Вопрос | Рабочее решение |
|---|---|
| Специализации кандидата | В интерфейсе одна активная специализация; модель данных допускает несколько независимых квалификаций |
| Грейды | JUNIOR, MIDDLE, SENIOR; UI: «грейд по результатам тестирования» |
| Первичная неудача | Подтверждённого грейда нет, в поиске кандидата нет |
| Переход на уровень ниже | После первичной неудачи можно сразу начать тест на более низкий грейд, если нет другого ограничения для этого грейда |
| Повторная попытка того же грейда | Не раньше чем через 24 часа после завершённой неуспешной попытки |
| Изменение подтверждённого грейда | Не раньше чем через 90 дней с последнего подтверждения/обновления квалификации |
| Высокий балл | Не повышает грейд автоматически; предлагает отдельное тестирование на следующий уровень после доступной даты |
| Провал повторной оценки | Не понижает и не удаляет ранее подтверждённый грейд |
| Извлечение навыков из вакансии | Структурированная форма и справочник навыков; автоматический NLP-разбор свободного текста не требуется |
| Тест под работодателя | Формирование плана теста из структурированных требований в рамках общей матрицы; отдельные дополнительные экзамены отложены |
| Приватность до согласия | Структурированная обезличенная карточка, без ФИО, прямых контактов, внешних ссылок и произвольных текстов резюме |
| Email локально | Реальное письмо в локальный Mailpit; для внешнего стенда предусмотрен SMTP через env |
| ФСП | Демонстрационный провайдер и синтетические достижения, явно помеченные как демонстрационные |

Параметры ограничений, порогов, длительности теста и весов подбора вынеси в серверную конфигурацию. Создай версию политики. Исторические результаты должны сохранять ту версию, по которой получены.

Если организаторы впоследствии дадут другие ответы, изменения должны вноситься в ограниченное число политик и сервисов, а не требовать переписывания интерфейса и базы.

## 5. Авторизация и роли

Роли: CANDIDATE и EMPLOYER. Один аккаунт имеет одну роль. Для MVP один работодатель управляет одной компанией; расширение до нескольких сотрудников компании опиши отдельно.

Регистрация: email, пароль, роль, согласие на обработку данных. Для работодателя — дальнейшее заполнение компании, для кандидата — профиля. Пароль хранить как безопасный адаптивный хеш, например Argon2id. Не хранить пароли или сессионные токены в открытом виде.

Используй серверные сессии PostgreSQL с криптографически случайным непрозрачным токеном в HttpOnly cookie. В базе хранить хеш токена, пользователя, срок действия, дату отзыва. В production cookie Secure, SameSite=Lax, Path=/; локально настройка должна позволять работу по HTTP. Не хранить токены авторизации в localStorage.

Обеспечь защиту изменяющих запросов от CSRF, проверку origin, ограничение частоты входа, регистрации и повторной отправки писем. Проверка роли и владения объектом всегда выполняется на backend.

Email подтверждается одноразовым токеном с TTL; в БД хранится его хеш. Переход по ссылке открывает экран подтверждения, который выполняет серверную операцию. Не делай необратимых изменений простым GET по ссылке письма. Неподтверждённый пользователь видит только экран подтверждения, повторную отправку и выход.

Выход отзывает сессию. Просроченная/отозванная сессия не даёт доступа. Клиентское скрытие меню не заменяет авторизацию API.

Локальный Mailpit используется для настоящего потока подтверждения. Seed-аккаунты могут быть заранее подтверждены и должны быть обозначены как демонстрационные. Нельзя делать универсальную кнопку обхода подтверждения или входа в production.

## 6. Профиль кандидата и онбординг

Поля собственного профиля:

- ФИО; контактный email, телефон, мессенджер — отдельные поля.
- Город, часовой пояс, допустимые форматы работы: REMOTE / HYBRID / OFFICE.
- Готовность рассматривать предложения: ACTIVE / PAUSED.
- Ожидаемая зарплата: необязательная вилка в RUB за месяц до вычета налогов.
- Отрасль интереса и специализация.
- Заявленный грейд.
- Стек из справочника, опыт в месяцах, роли, описание опыта, soft skills, внешние ссылки.
- Согласие на обработку данных, отдельное согласие на публикацию профиля работодателям, время и версия каждого согласия.
- Настройки видимости и выбранные каналы контакта для раскрытия после принятия приглашения.

Не называй самоописанные опыт, стек и soft skills подтверждёнными. Для навыков показывай источник: «указано кандидатом» / «проверено тестом». Достижения ФСП показываются отдельным блоком.

Онбординг: подтверждение email → профиль → опрос → выбор специализации и заявленного грейда → объяснение тестирования → тест → результат → настройки публикации.

Храни прогресс. Незавершённый профиль не теряется после перезагрузки. Перед тестом показывай длительность, правила, текущие ограничения и доступность следующей попытки.

Кандидат попадает в поиск только если одновременно:

1. Email подтверждён.
2. Обязательные поля заполнены и выбран хотя бы один канал контакта для приглашений.
3. Есть опубликованное согласие на видимость профиля и `isDiscoverable=true`.
4. Статус готовности ACTIVE.
5. Есть подтверждённая квалификация по активной специализации.

Изменение самоописанного грейда не меняет подтверждённую квалификацию. Изменение активной специализации не переносит на неё результат другой специализации. Для новой специализации нужен отдельный тест.

## 7. Механика тестирования

### 7.1. Справочник компетенций

В каждой специализации выдели три основные группы навыков:

| Специализация | Группа 1 | Группа 2 | Группа 3 |
|---|---|---|---|
| FRONTEND | JavaScript/TypeScript и асинхронность | Состояние и поведение интерфейса | HTTP/API и обработка ошибок клиента |
| BACKEND | API и обработка запросов | SQL и моделирование данных | Транзакции, конкурентность и надёжность |
| ML_ENGINEER | Подготовка данных и утечки | Метрики и оценка моделей | Валидация, выбор модели и эксплуатационные сценарии |
| MANUAL_QA | Анализ требований | Границы и классы эквивалентности | Тест-кейсы, дефекты и приоритизация |

Введи конкретные теги навыков внутри групп, чтобы требования работодателя сопоставлялись с проверяемыми навыками. Нельзя делать вывод «NestJS подтверждён» только из общего успешного теста по backend. Для технологического тега нужны задания, действительно его проверяющие.

### 7.2. Банк и генерация вариантов

Задания генерируются алгоритмически из проверенных семейств. Используй серверный контракт примерно такого вида:

```ts
interface AssessmentFamily {
  id: string;
  version: number;
  specialization: Specialization;
  group: CompetencyGroup;
  supportedGrades: Grade[];
  skillTags: string[];
  generate(input: GenerationInput): PrivateTaskInstance;
  evaluate(task: PrivateTaskInstance, answer: SubmittedAnswer): Evaluation;
}
```

`PrivateTaskInstance` содержит отдельно публичные условия и закрытый ключ проверки. На клиент сериализуются только публичные поля и схема допустимого ответа. Клиент не передаёт результат, грейд или начисленные баллы как доверенные значения.

Для каждой специализации подготовь минимум по два независимых семейства на каждую из трёх групп: всего минимум 24 семейства. У каждого семейства должны быть осмысленные варианты для всех трёх грейдов. Разница грейдов — в проверяемом рассуждении и условиях, а не только в размере чисел.

Для каждой комбинации семейства и грейда генератор должен давать не менее 30 различающихся допустимых экземпляров. Это минимальный демонстрационный банк, не доказательство промышленной защищённости.

Меняй исходные данные, граничные условия, зависимости, сценарии и варианты решений. Одна перестановка ответов не считается новым экземпляром. Для каждого экземпляра вычисляй fingerprint значимых условий. Не выдавай кандидату точный повтор ранее предъявленного экземпляра при наличии альтернатив. Отдельно фиксируй повторяемость семейств — она неизбежна при небольшом банке.

Генерация воспроизводима по серверному seed, версии семейства и параметрам. Сохраняй неизменяемый снимок выданной задачи и ключа оценки, чтобы изменение банка не влияло на начатые и завершённые попытки. Не используй Math.random как источник токенов безопасности.

Генератор не должен выполнять произвольный код из ответа пользователя. Строка кода в задании — материал для анализа; правильный результат определяется контролируемой серверной логикой.

### 7.3. Форматы и оценка

Поддержи SINGLE_CHOICE, MULTI_SELECT, NUMERIC, MATCHING и ORDERING. Используй только форматы, нужные реальным заданиям; минимум три разных формата во всём банке.

Свободный текст можно добавить как необязательное пояснение кандидата, но не начислять за него автоматические баллы без реализованной надёжной проверки.

Шаблоны примеров:

- Frontend: порядок асинхронных операций, ошибочные переходы состояния, гонка запросов, корректное отображение ошибки API.
- Backend: результат SQL на сгенерированных таблицах, обработка повторного запроса, конфликт транзакций, выбор семантики HTTP.
- ML: матрица ошибок и метрика, утечка при подготовке данных, временное разделение выборки, выбор оценки при дисбалансе.
- QA: границы параметров формы, комбинации требований, минимальный достаточный набор проверок, отличия severity и priority в заданном контексте.

Один тест содержит шесть мини-кейсов: по два из каждой группы. В кейсе может быть несколько проверяемых частей; минимум 12 оцениваемых частей на тест. По возможности не повторяй семейство внутри попытки. Длительность по умолчанию 30 минут, настраиваемая.

За атомарный ответ SINGLE_CHOICE, MULTI_SELECT, MATCHING, ORDERING по умолчанию начисляется 0 или 1; для MULTI_SELECT требуется точное множество. NUMERIC проверяется по заданному допуску. Частичный балл допускается только через явно выделенные независимые части, не через скрытую эвристику. Нельзя получить полный балл, выбрав все ответы.

Считай балл каждой группы от 0 до 100, общий балл — среднее трёх групп. Проходной критерий: общий балл не менее 75 и каждая группа не менее 50. «Уверенное прохождение»: общий не менее 90 и каждая группа не менее 75. Эти пороги конфигурируемы и не выданы за научно откалиброванные.

Подтверждение конкретного skillTag допускается, когда он реально оценён минимум в двух разных кейсах и результат по нему не менее 70. Если покрытия недостаточно, тег имеет статус «недостаточно данных», даже при высоком общем результате. Не используй оценки неуспешной попытки как новую подтверждённую квалификацию.

### 7.4. Жизненный цикл попытки

Статусы: IN_PROGRESS, PASSED, FAILED, EXPIRED, ABANDONED. Завершённая попытка неизменяема.

- Создавай попытку и снимки заданий транзакционно.
- Не допускай более одной активной попытки у кандидата; защити и конкурентные запросы.
- Таймер определяется серверным `expiresAt`. Перезагрузка не продлевает время.
- Ответы сохраняются на сервере с debounce; при восстановлении отображается принятый сервером вариант.
- Устаревший autosave не должен перезаписывать более свежий: используй номер ревизии или аналогичный контроль конкурентности.
- Завершение сначала синхронно сохраняет актуальные ответы, затем фиксирует результат. Нельзя потерять последнюю правку из-за debounce.
- Повторный submit возвращает тот же результат, не создаёт новую квалификацию.
- При истечении времени попытка получает EXPIRED, баллы по сохранённым ответам показываются для обратной связи, но квалификация не выдаётся.
- Просроченность проверяется и при чтении/изменении, а не только фоновым заданием.
- Выход из страницы не завершает попытку; явное «Прервать» создаёт ABANDONED и не позволяет обходить задержку пересдачи.
- Во время теста не раскрывай правильность промежуточных ответов.
- После теста показывай группы навыков, баллы, статус и рекомендации для обучения. Не отдавай полный закрытый банк и ключи проверки.

### 7.5. Политика пересдач и подтверждения

Для специализации без подтверждённого грейда: первая попытка доступна сразу. После FAILED / EXPIRED / ABANDONED повтор той же комбинации специализация+грейд доступен через 24 часа. Более низкий грейд можно выбрать сразу, если его собственная задержка не действует.

Первый PASSED создаёт подтверждённую квалификацию и `nextReassessmentAt = now + 90 дней`. До этой даты новую официальную оценку этой специализации не начинай. Для другой специализации ограничение независимо.

После доступной даты кандидат может пройти отдельный тест на выбранный грейд. Неуспех оставляет старую квалификацию; повтор того же уровня ограничен 24 часами. Успех обновляет квалификацию и новую дату через 90 дней, включая успешное подтверждение того же грейда.

При осознанном выборе более низкого грейда после срока ограничения предупреди, что успешный результат заменит активный грейд. Автоматически понижать нельзя. В истории сохраняются все подтверждения.

Высокий балл не присваивает следующий грейд. UI предлагает его отдельную проверку и показывает доступную дату.

В UI отображай точную причину запрета и дату следующей доступной попытки. Для демонстрации истечения сроков используй заранее подготовленную историю и внедряемые часы в тестах; не создавай общедоступный API сброса ограничений.

## 8. Потребности работодателя и формирование тестов

Компания: название, описание, отрасль, сайт, контактное лицо и способ связи. Не выдавай её за верифицированную: такой проверки в MVP нет.

Работодатель создаёт HiringNeed:

- Название и описание команды/задач.
- Одна специализация.
- Явный список допустимых грейдов, например [MIDDLE, SENIOR]. Не считай Senior автоматически подходящим для Junior.
- Обязательные проверенные навыки.
- Желательные навыки с источником SELF_REPORTED_ALLOWED или VERIFIED_ONLY.
- Формат работы и город, если требуется присутствие.
- Зарплатная вилка в RUB за месяц, `salaryFrom <= salaryTo`, положительные целые значения, обязательное обозначение GROSS.
- Статус DRAFT / ACTIVE / ARCHIVED.

Наличие опубликованной вакансии не требуется. HiringNeed — внутреннее описание потребности, доступное только компании.

Подготовь минимум восемь содержательных примеров потребностей — по два на каждую специализацию. На них покажи механизм `buildAssessmentBlueprint(need, grade)`:

1. Валидировать структурированные навыки по справочнику.
2. Сопоставить их с компетенциями и семействами банка.
3. Построить план, сохраняющий три обязательные группы и правила сложности выбранного грейда.
4. Показать связь «требование → проверяемый навык → семейство задачи».
5. Пометить требования, для которых ещё нет проверяющих заданий, как непокрытые. Не подменять их случайными задачами.

Обычный регистрационный тест строится по общему blueprint специализации. Для демонстрации построения теста из потребности добавь работодателю предпросмотр плана и образцов условий без правильных ответов. Этот предпросмотр не меняет грейд кандидата и не открывает дополнительный обязательный экзамен под каждого работодателя. Отдельно опиши это ограничение.

Параметры требований могут выбирать семейства и прикладной контекст, но не должны незаметно менять пороги и сложность официального грейда. Если банк мал и выбрать альтернативное семейство невозможно, сообщи об этом в отчёте покрытия.

## 9. Поиск, ранжирование и объяснения

Два режима: общий банк кандидатов и подбор по выбранной HiringNeed.

Общий банк фильтруется по активной специализации, подтверждённому грейду, категории, навыкам, источнику подтверждения навыков, формату работы, наличию достижений ФСП. Кандидат не имеет доступа к банку.

Для подбора сначала применяются обязательные условия:

- Видимость кандидата и подтверждение email.
- Подтверждённая специализация и один из допустимых грейдов.
- Все навыки, обозначенные работодателем как обязательные проверенные.
- Совместимость формата и города при наличии соответствующего ограничения.
- Пересечение зарплатных вилок, если кандидат задал ожидания. Если ожидания не заданы, не исключать; показывать «ожидания не указаны».

ФСП, самоописание или высокий общий балл не могут компенсировать провал обязательного условия. При пустой выдаче покажи причины и предложи работодателю явно изменить фильтры, не ослабляй их автоматически.

Для прошедших фильтры вычисляй компоненты 0..1:

- `preferredFit`: среднее соответствие желательным навыкам. Подтверждённый навык = 1; только заявленный = 0.3, если режим навыка это допускает; иначе 0. Если желательных навыков нет, компонент одинаков для всех и равен 1.
- `assessmentQuality`: общий балл активного подтверждения / 100. Между разными грейдами это технический показатель MVP, а не доказанная психометрическая сопоставимость; ограничение отразить в документации.
- `fspEvidence`: ограниченный бонус по релевантным достижениям, нормированный 0..1.

Формула MVP: `score = 70 * preferredFit + 25 * assessmentQuality + 5 * fspEvidence`.

Релевантность достижения специализации задаётся версионируемым справочником. За релевантное участие — 1 балл, призовое место — 2, победу — 3; для одного мероприятия учитывается только сильнейшая запись. Нормировка `min(sum / 6, 1)`. Нерелевантное достижение можно показать в профиле, но оно не даёт бонуса этой подборке. Отсутствие ФСП означает нулевой бонус, а не запрет доступа.

Для общего банка используй сортировку по специализации и грейду, внутри категории — `95 * assessmentQuality + 5 * fspEvidence`. Не перемешивай категории так, будто числовой балл полностью отражает разницу грейдов.

Стабильное разрешение равенств: общий score → результат теста → идентификатор кандидата. Источник и версия формулы должны сохраняться с подборкой.

Возвращай структурированное объяснение: пройденные обязательные условия, совпавшие желательные навыки и источник доказательства, непроверенные навыки, вклад компонентов, совпадение условий и зарплаты. Не называй score вероятностью найма или «процентом профессиональной пригодности».

В UI выдели «Почему подходит» и «Что пока не подтверждено». Объяснения собираются из реальных данных правил, без LLM и без выдуманных причин.

### Сохранение подборки

Фильтры отражаются в URL. Каждое построение по HiringNeed сохраняется как SelectionRun: версия потребности, фильтры, формула, время, отсортированные идентификаторы и безопасные объяснения. Уточнение создаёт новую версию, предыдущая доступна через историю. Закладки кандидатов сохраняются отдельно и не пропадают от изменения фильтров.

При открытии старой подборки повторно проверяй текущие права и видимость. Скрытый кандидат отображается как недоступный без старых деталей; запрещено раскрывать отозванные данные через снимок. Контакты никогда не хранятся в снимках подбора.

## 10. Приглашения и раскрытие контактов

Приглашение создаётся из карточки кандидата. Поля: компания, кандидат, необязательная HiringNeed, заголовок предложения, описание задач/условий, зарплата от/до в RUB за месяц GROSS, формат работы, способ связи с работодателем.

Даже без HiringNeed все обязательные поля доступны вручную. Нельзя требовать публикации вакансии.

Статусы и переходы:

```text
SENT -> VIEWED                         кандидат явно открыл приглашение
SENT / VIEWED -> ACCEPTED              кандидат принял
SENT / VIEWED -> DECLINED              кандидат отказал
SENT / VIEWED -> WITHDRAWN             работодатель отозвал
SENT / VIEWED -> EXPIRED               истёк срок действия
```

TTL по умолчанию 14 дней. Просроченность проверяется сервером при действиях; браузерный таймер не источник истины. Финальные статусы не переходят друг в друга.

После отправки предложение неизменно. При изменении условий нужно отозвать активное приглашение и создать новое. Сохраняй снимок предложения и данных компании для истории, но не добавляй в него приватные данные кандидата.

Не допускай более одного активного SENT/VIEWED приглашения от компании этому кандидату. Повторная отправка, двойной клик и параллельные accept/withdraw должны обрабатываться атомарно. Повтор того же успешного действия идемпотентен, противоречащее финальному статусу действие возвращает 409.

Принятие приглашения транзакционно:

1. Проверяет адресата, состояние, срок и владение объектом.
2. Фиксирует ACCEPTED и событие истории.
3. Создаёт/активирует ContactAccessGrant именно для пары candidate+company.
4. Показывает обеим сторонам доступные каналы связи.

Перед подтверждением кандидат видит точную зарплату, условия и список данных, которые будут раскрыты. Доступ не распространяется на других работодателей.

Открытие списка приглашений или frontend-prefetch не переводит их все в VIEWED. Для фиксации просмотра используй отдельное явное действие.

Кандидат видит компании с выданным доступом и может отозвать дальнейший доступ. Отзыв не меняет исторический ACCEPTED, но закрывает контакты в новых API/PDF-ответах. Уже полученную работодателем копию данных технически отозвать невозможно; объясни это кратко в интерфейсе.

Скрытие профиля исключает новый поиск, но само по себе не отзывает ранее выданные доступы — для этого отдельное действие. После явного отзыва повторный идемпотентный accept старого приглашения не должен незаметно выдавать доступ заново. Новый доступ возможен только через новое осознанное согласие.

Обе стороны видят свои актуальные статусы. Достаточно обновления при возвращении на вкладку и умеренного polling; WebSocket не нужен.

## 11. Приватность и PDF

Сделай единый серверный сервис представления профиля с режимами OWNER, EMPLOYER_REDACTED, EMPLOYER_GRANTED. Его используют JSON API и PDF, чтобы правила не расходились.

До выдачи ContactAccessGrant работодателю доступны только:

- Системный псевдоним вида «Кандидат A17F» и нейтральный аватар.
- Специализация, подтверждённый грейд, оценённые навыки и баллы.
- Структурированные самоописанные навыки с соответствующей маркировкой.
- Город, формат работы, зарплатные ожидания при их заполнении.
- Обезличенные сведения о достижениях: тип, уровень, место, год, релевантные навыки.

До согласия запрещены ФИО, email, телефон, мессенджеры, ФСП ID, фотографии, URL профилей/портфолио, названия прошлых работодателей и произвольное описание опыта. Не пытайся гарантировать анонимность произвольного текста простым regex — в редактированную карточку его вообще не включай.

Обезличивание снижает прямую идентифицируемость, но не даёт гарантии анонимности по совокупности признаков. Не заявляй такую гарантию.

Владелец скачивает полный PDF своего профиля. Работодатель скачивает только соответствующую его правам версию. PDF генерируется backend после проверки доступа; ссылка не публичная. Приватные ответы и PDF — `Cache-Control: private, no-store`.

Используй локальный шрифт с кириллицей и библиотеку PDF, не требующую внешнего API. Проверь длинные имена, многострочные значения, переносы страниц и отсутствие скрытых контактов в тексте/метаданных обезличенного PDF. Не включай ФИО в имя такого файла.

Не выдавай полные ORM-объекты наружу. DTO для разных прав должны иметь явные разрешённые поля. Проверяй реальные API-ответы, а не только скрытие текста на странице.

## 12. Интеграция ФСП

Реальный API и схема данных ФСП отсутствуют. Реализуй интерфейс провайдера и локальную реализацию MockFspProvider. Модель не должна зависеть от конкретного внешнего JSON.

Пример достижений: externalId, eventId, eventTitle, discipline, eventLevel, eventDate, participationType, place, teamRole, skillTags, source, verifiedAt. Поля необязательны там, где источник может их не давать; не придумывай отсутствующие значения.

Для привязки в деморежиме кандидат вводит тестовый ФСП ID и одноразовый демонстрационный код из подготовленной fixture. Только ввод чужого ID не должен давать чужие достижения. На экране написано «Демонстрационная интеграция»; синтетические записи не называй реально подтверждёнными федерацией.

Состояния: NOT_LINKED, LINKED_WITH_HISTORY, LINKED_WITHOUT_HISTORY, SYNC_ERROR. При ошибке синхронизации не удаляй последнюю успешную историю и показывай дату обновления. Отвязка убирает текущий бонус ФСП и прекращает отображение связанной истории работодателям.

Не смешивай идентификацию через будущий Keycloak с получением достижений: опиши отдельно OIDC-связь issuer+subject с локальным userId и внешний API данных. В MVP Keycloak не разворачивай.

Сначала корректная фильтрация и сортировка, потом пагинация. Нельзя ранжировать только первую произвольную страницу кандидатов. Для объёма синтетического MVP допустим расчёт score в backend после SQL-фильтрации, с измерением времени; ограничения масштабирования опиши.

## 15. Интерфейс

Язык интерфейса — русский. Сделай спокойный, современный сервис найма: светлая основа, фиолетовый акцент, читабельная типографика, ясные статусы. Если брендбук/логотип ФСП не предоставлен, не выдумывай официальный знак; используй текстовое название и локальные нейтральные иконки.

Главная показывает смысл сервиса и два входа: «Я ищу работу» / «Я ищу специалиста». Не делай сложный маркетинговый сайт в ущерб кабинетам.

Кандидат:

- Главная кабинета: прогресс онбординга, подтверждённая категория, доступность оценки, новые приглашения.
- Редактор профиля с явным разделением заявленных и подтверждённых данных.
- Пошаговый опрос и выбор грейда.
- Экран теста: прогресс, серверный таймер, автосохранение, навигация, предупреждение перед отправкой.
- Результат: общий балл, три группы навыков, статус, доступная следующая дата.
- История оценок.
- Входящие приглашения с заметной зарплатой и условиями до принятия.
- Настройки приватности, список компаний с доступом, связь ФСП, скачивание PDF.

Работодатель:

- Профиль компании.
- Список потребностей и форма создания.
- Подборка: фильтры, краткие карточки, объяснения, закладки, сохранённые версии.
- Карточка кандидата с блоками «Подтверждено», «Указано кандидатом», «Что не проверено».
- Форма предложения с обязательной вилкой и предварительным просмотром.
- Список отправленных приглашений и статусов.
- Предпросмотр покрытия потребности тестовыми заданиями.

Для всех экранов нужны реальные loading/error/empty/forbidden-состояния, понятная валидация, работа клавиатурой, видимый фокус и достаточный контраст. Основной целевой формат — desktop; базовое поведение на узких экранах без горизонтального развала желательно, отдельный мобильный продукт не нужен.

Не отображай фиктивные счётчики, неработающие кнопки и статичные успехи вместо API. Демонстрационные данные должны храниться в PostgreSQL и проходить через настоящую бизнес-логику.

## 16. Синтетические данные

Сделай воспроизводимый seed с фиксированным seed генерации, идемпотентными идентификаторами и безопасными демонстрационными адресами. Не используй реальные персональные данные.

Базовый демонстрационный набор:

- 96 кандидатов: минимум 8 на каждую комбинацию 4 специализации × 3 грейда.
- Дополнительно кандидаты без подтверждения, с провалом, скрытым профилем, неподтверждённым email, незаполненным профилем и истёкшим экзаменом.
- 4 компании и минимум 8 потребностей.
- Кандидаты с ФСП, без привязки, с привязкой без истории, с ошибкой синхронизации.
- Разные результаты по группам навыков, зарплатные ожидания и форматы работы.
- Приглашения во всех состояниях и случаи доступа только одной компании.
- Несколько сохранённых подборок и закладок.

Не генерируй «подтверждённые» грейды только присваиванием поля случайному пользователю. Подготовь синтетические попытки и ответы, рассчитай результаты тем же серверным evaluator и из них создай квалификации. Для границ и исторических состояний разрешены явно обозначенные фикстуры.

Пароли демоаккаунтов передавай через `.env` или явно обозначенный локальный seed. Опубликуй тестовые логины в README только для деморежима; не запускай seed автоматически при production-старте.

## 17. Валидация качества

Создай исполняемый скрипт `pnpm validate:quality`, который считает показатели по отдельным данным и формирует `docs/validation-results.json` и читаемый отчёт `docs/validation-results.md`. Отчёт содержит seed, commit/версию, объёмы выборок, версии правил и время запуска. Не пиши придуманные результаты до фактического выполнения.

### Подбор

- Создай не менее 12 оценочных потребностей, по 3 на специализацию, отличающихся от демонстрационных.
- Подготовь независимую явную разметку пар need-candidate: 0 — не подходит, 1 — допустим, 2 — хорошо подходит, с объяснением.
- Разметку задавай по отдельным сценариям и ожидаемому смыслу, не вычисляй текущей формулой score. Не копируй алгоритм подбора в «эталон».
- Раздели сценарии настройки и итоговой проверки; зафиксируй веса до финального прогона. Укажи, что разметка авторская синтетическая, не экспертная внешняя.
- Считай Precision@5, nDCG@5, долю нарушений обязательных условий и покрытие потребностей непустой выдачей.
- Для списков короче 5 явно документируй знаменатель. По умолчанию Precision@5 делит число релевантных на 5; отдельно показывай precision по фактически возвращённым результатам.
- Сравни с простым baseline: фильтрация по специализации/грейду и сортировка по общему баллу теста.
- Не обещай улучшение заранее. Если baseline лучше, покажи это и объясни ограничения.

### Тестирование

- Проверяй корректность генерации и отсутствие неразрешимых/неоднозначных экземпляров на фиксированном наборе seed.
- У каждого семейства/грейда должны быть вручную заданные контрольные примеры, включая неверный и граничный ответ; не проверяй генератор только им самим.
- Воспроизводимость: одинаковые версии и seed дают одинаковое условие и оценку.
- Правильные ответы проходят пороги; явно неверные не проходят; выбор всех вариантов не даёт полного балла.
- Синтетические профили слабого, среднего и сильного решателя используй только для симуляционного анализа. Измерь разброс баллов между вариантами, согласованность pass/fail и зависимость от группы навыков.
- Покажи частоту точных повторов и пересечение семейств между попытками. Не называй параметризацию полной защитой от списывания.
- Отдельно укажи: синтетика проверяет реализованные правила, но не доказывает соответствие грейда реальной квалификации человека, психометрическую эквивалентность заданий или устойчивость к помощи LLM.

Если выполняешь нагрузочный прогон, сохраняй окружение, объём данных, число виртуальных пользователей, p50/p95 и ошибки. Ориентир для основных API поиска/профиля — p95 до 1 секунды на 1000 синтетических кандидатов и 20 параллельных пользователей на указанной тестовой машине; это целевой показатель проекта, а не уже достигнутый факт. PDF и тестовую генерацию измеряй отдельно.

## 18. Обязательные автоматические проверки

Пиши тесты для реальных рисков бизнес-логики, а не ради процента покрытия.

Unit/integration:

- Граница 74/75 по общему баллу, минимальный балл каждой группы, уверенное прохождение.
- Нельзя подтвердить навык без достаточного покрытия.
- Нельзя автоматически понизить грейд после неудачи.
- Даты ограничений, границы 24 часов/90 дней, независимость специализаций.
- Конкурентный старт двух попыток; повторный submit; серверный timeout; устаревший autosave.
- Обязательные навыки и зарплата отсекают неподходящего кандидата; ФСП не отменяет фильтр.
- Ранжирование и стабильная пагинация не меняются от размера страницы.
- Скрытый профиль не раскрывается через старую подборку или закладку.
- Кандидат не видит чужие результаты, приглашения и анкеты.
- Работодатель не видит чужие потребности/приглашения.
- До ACCEPTED контактов нет в JSON/PDF; после принятия они есть только у нужной компании.
- Одновременные accept/withdraw, повторное принятие, истечение и отзыв доступа.
- ФСП без истории и ошибка провайдера не ломают онбординг и поиск.

E2E через Playwright либо эквивалент:

1. Новый кандидат регистрируется, подтверждает email через Mailpit, заполняет профиль, проходит тест, получает категорию и публикуется.
2. Работодатель создаёт потребность, видит подходящего кандидата, объяснение и скрытые контакты, отправляет предложение.
3. Кандидат видит зарплату, принимает; первая компания получает контакты, другая не получает.
4. Неуспешная первая попытка не публикует профиль и позволяет корректный путь к более низкому грейду.
5. Кандидат без ФСП проходит весь основной сценарий.

Для E2E правильные ответы получай из тестовых fixture/серверного тестового helper, не создавай production endpoint выдачи ключей. Не отключай security guards ради прохождения тестов.

Запусти lint, typecheck, build, unit/integration и доступные E2E. Если окружение не позволяет выполнить часть проверки, сообщи точную причину и команду для воспроизведения. Не отмечай невыполненную проверку как успешную.

## 19. Запуск, документация и демонстрация

Docker Compose: web, api, postgres и mailpit. Mailpit — локальный/демонстрационный профиль; его интерфейс нельзя бездумно выставлять публично. Внешний запуск использует настроенный SMTP и HTTPS.

База имеет volume и healthcheck. Миграции выполняются воспроизводимой командой/одноразовым сервисом до запуска API. Перезапуск не стирает данные. Не используй `db push` вместо истории миграций в итоговом сценарии.

Добавь `.env.example` со всеми переменными, без секретов. Минимум: DATABASE_URL, APP_ORIGIN, API_INTERNAL_URL, настройки session cookie, SMTP, режим ФСП, seed/config политик. Приложение валидирует обязательную конфигурацию при старте и выводит понятную ошибку.

Ожидаемые команды: install, dev, build, lint, typecheck, test, test:integration, test:e2e, db:migrate, db:seed, validate:quality, docs:export. Допустимы другие имена при однозначном описании.

Подготовь:

- `README.md`: назначение, быстрый запуск, env, миграции, seed, тестовые учётные записи, команды, ограничения.
- `docs/architecture.md`: компоненты, модули, модель данных и ключевые потоки.
- `docs/assessment.md`: банк, параметры сложности, оценка, политика грейдов, защита от повторов, ограничения.

Проверь читаемость кириллицы и таблиц. Если конвертер недоступен в текущей среде, явно зафиксируй блокер и не объявляй сдачу полностью готовой.

## 20. Этапы реализации

1. Основа: репозиторий, зависимости, Compose, схема, миграции, конфигурация, healthcheck, авторизация и роли.
2. Вертикальный путь кандидата для одной специализации: профиль, опрос, экзамен, результат, приватность.
3. Путь работодателя: компания, потребность, подбор, объяснение, приглашение, принятие и доступ к контактам.
4. Все четыре специализации и грейды, полноценный банк параметризованных задач, история, пересдачи, ФСП и PDF.
5. Сохранение подборок, закладки, обработка конфликтов/ошибок, синтетические сценарии и UI-полировка.
6. Валидация, ключевые тесты, исправления, документация и воспроизводимый демонстрационный запуск.

После каждого этапа отмечай фактический результат и команды проверки. Не трать первый этап на сложную дизайн-систему или инфраструктуру будущих функций.

Для работы двух разработчиков выдели зоны ответственности в документации: кандидат+assessment и работодатель+matching+invitations. Общие модели, авторизацию и контракт согласуй в коде на раннем этапе. Не создавай две несовместимые реализации общих сущностей.

## 21. Критерии готовности

MVP готов к технической демонстрации, когда:

1. На чистой машине по инструкции поднимаются frontend, backend, PostgreSQL и локальная почта; миграции и seed работают повторяемо.
2. Две роли реально изолированы на API и UI.
3. Доступны все четыре специализации и три грейда, а не только названия в select.
